1

window.confirm はなぜブロックされたか

§17 §18
症状

window.confirmによる削除確認が常にfalse判定になり、削除処理が中断していた。

仕組み

confirm/alert/promptはJSの実行を同期的に止める「ブロッキングダイアログ」で、呼び出し中はイベントループ全体が止まる。Chromeは同一タブから短時間に連続してこれらが呼ばれると「このページはこれ以上ダイアログを表示できません」として以後を無条件にブロックする仕様を持っており、拡張機能やページの状態次第でも抑止される。さらにPuppeteerのような自動操作環境ではデフォルトでダイアログに応答できず、そもそも動作しない。Reactのような非同期の再描画前提のフレームワークと、同期でスレッドを止めるAPIは設計思想が根本的に噛み合っていない。

次に活きる視点

同期ブロッキング系のブラウザAPI（confirm/alert/prompt、同期XHR）は「レガシーで使用禁止」と最初から扱い、確認UIは常に自前のモーダルコンポーネントで設計する。イベントループの基礎（マイクロタスク・マクロタスクと、同期呼び出しがそれらをどう塞ぐか）を理解していると、この種の不具合は実装前に避けられる。

2

不正バイト列はどこから来たか

§31
症状

lib/subItemUtils.tsに不正なバイト列が混入し、開発サーバー起動時にパースエラーが発生した。

仕組み

ソースファイルはUTF-8のバイト列として保存されているが、JS文字列はランタイム内部ではUTF-16で扱われる。全角括弧や丸数字のような非ASCII文字をコピー＆ペーストする経路（別エンコーディングのクリップボード、PDFからの抽出、一部のAI出力）で、Unicodeのコードポイントとしては正しくてもUTF-8のバイト列としては壊れた並びが紛れ込むことがある。ツールによってはこれを黙って置換文字（U+FFFD）に変換し、TypeScriptのコンパイラやNode.jsのファイル読み込みはそれを前提に読むため、症状が「起動時のパースエラー」という遠い場所で出る。加えて[...str.matchAll(regex)]のようなイテレータのスプレッドは、TypeScriptのコンパイル対象（tsconfig.jsonのtarget/lib）によってはダウンレベル変換がうまくいかず、実行時に落ちることがある—文字コードの問題とは別系統の罠として同時に踏んでいる。

次に活きる視点

Unicodeコードポイント・UTF-8バイト列・JS内部表現(UTF-16)の3層を区別して理解しておくと、「表示は正しいのに保存すると壊れる」系の不具合の当たりが早くつく。あわせてtsconfig.jsonのtarget/libが何をポリフィル・ダウンレベルするか（イテレータプロトコルなど）を一度確認しておくと、同種の実行時エラーを事前に避けられる。

3

SVG座標は目分量ではなく制約から導く

§10
症状

「円に内接する四角形」の初期SVG座標が目分量で、頂点が円周上からズレていた。

仕組み

円周上の点は (x-cx)² + (y-cy)² = r² という制約を満たす必要がある。目分量で座標を置くとこの制約は見た目上わずかにしか崩れないため、レンダリング結果を見ただけでは気づきにくい。修正では中心(80,60)・半径50の円に対し、ピタゴラス数（14²+48²=50²、30²+40²=50²）を使って整数座標を機械的に導出している—これは「円周上の格子点を求める」という典型的なテクニックで、目分量を排除して制約そのものをコードに落とし込んだ好例。

次に活きる視点

座標・配点・日付計算など「守るべき制約」がある数値は、たとえ一度きりの値であっても目分量で置かず、制約を満たす式（またはそれを検算する一行）をコードとして残す。「導出できる値は導出する、推測しない」という姿勢はこの案件に限らない一般原則。

4

「ビルドが通る」が保証する範囲とテストピラミッド

§10 §17 §31
症状

毎回npm run buildのエラー0件を確認しているにもかかわらず、3件のバグはユーザーが最初に踏んでいる。

仕組み

tscやバンドラのビルド成功が保証するのは「型が整合している」「構文が正しい」「モジュール解決ができる」ことだけで、正規表現が意図した文字列にマッチするか、DOMが期待通り更新されるか、ブラウザ固有の挙動（印刷エンジン・ダイアログの抑止）がどう振る舞うかは一切検証しない。この案件の「検証」は実質的に型検査とスクリーンショット目視の2層のみで、その中間にあるべき「関数単体が期待通りの入出力を返すか」を機械的に固定する層（ユニットテスト）が存在しない。特にparseSubItemsやfuzzySearchMatchのような正規表現主体のロジックは、入力パターンの数だけ分岐が増え、目視確認だけでは網羅しきれない。

次に活きる視点

テストピラミッド（ユニット→結合→E2E/手動確認）という考え方を持ち、lib/配下の純粋関数のような「入力→出力が決定的」なコードから優先的にユニットテストを敷く。今回踏んだ3件のバグは、いずれも代表的な入力ケースを数行のテストとして固定していれば型検査の段階で拾えていた種類のもの。

5

Undo実装：スナップショット方式とコマンドパターン

§18
症状

Ctrl+ZのUndoを、変更直前の状態をまるごと配列に積むtestHistoryスタックで実装している。

仕組み

Undo実装には大きく2方式ある。ひとつは今回採用された「スナップショット方式」で、変更のたびに状態全体のコピーを履歴に積み、戻すときはそのコピーに丸ごと差し替える。実装が単純な反面、状態が大きいほどメモリを消費する。もうひとつは「コマンドパターン」で、変更そのものではなく変更の逆操作（例：追加なら削除、削除なら復元に必要な情報）だけを履歴に積む。メモリ効率は良いが、すべての操作に逆操作を書く必要があり実装コストが高い。今回はテストデータがJSON数十問程度で状態サイズが小さいため、スナップショット方式を選んだのは規模に対して正しい判断だった。

次に活きる視点

Undoを実装するたびに「このデータ規模ならどちらが妥当か」を毎回一から考えるのではなく、判断基準（状態サイズ・操作の可逆性コスト・実装工数）を一度言語化しておくと、次にUndoが必要な機能が出たときに即決できる。

6

印刷はスクリーンとは別のレンダリングパイプライン

§27 §28
症状

2ページ目以降が印刷されない、B4の2in1印刷でレイアウトが崩れる、という不具合が連続して発生した。

仕組み

ブラウザの印刷は「CSS Paged Media」という、画面表示とは別のレンダリング仕様に従う。親要素のoverflow:hiddenやheight固定は画面上はスクロールで隠れているだけに見えても、印刷エンジンはページ送りの計算をする前にその制約をそのまま適用するため、2枚目以降がまるごと切り捨てられる。用紙サイズや向きは@page { size: ... }という別のat-ruleで制御され、通常のレイアウトCSSとは独立している。2in1縮小印刷はOS/プリンタドライバ側がA4の完成形を機械的に縮小して並べるだけなので、A4自体の寸法（210mm × 297mm）を!importantで固定してブラウザ・アプリ側の計算揺れを排除したのが正しい対処。

次に活きる視点

「画面で正しく見える」ことと「印刷で正しく出る」ことは別のレンダリング経路だと最初から意識し、印刷対応が要件に入った時点で早めに@media printと実際の印刷プレビュー（Ctrl+P）で検証する。CSS Paged Mediaの仕様（@page、break-before/break-after、overflowの扱い）を一度通読しておくと勘に頼らず原因特定できる。

次への学習ロードマップ

  1. lib/配下にVitestを導入する。 parseSubItems fuzzySearchMatch generateSectionTitleFromQuestions pageUtilsの重み計算など、正規表現・文字列処理主体の純粋関数から着手する。まずは既に踏んだ3件のバグ（UTF-8混入、全角括弧誤検出、範囲表記の誤補正）を再現するケースをテストとして固定すると、投資対効果が高い。

  2. 文字コードの基礎を一度体系的に読む。 Unicodeコードポイント・UTF-8バイト列・JS内部のUTF-16表現の関係と、TypeScriptのtarget/lib設定が何をダウンレベルするかを押さえておく。

  3. 同期ブロッキング系ブラウザAPIを「使用禁止リスト」として明文化する。 confirm/alert/promptや同期XHRは最初からカスタムUIで代替する方針をデフォルトにする。

  4. CSS Paged Mediaの仕様を一度通読する。 @page、break-after、印刷時のoverflowの扱いを理解しておき、印刷まわりの不具合が出た時に勘ではなく原典に当たれるようにする。

  5. Undoのスナップショット方式とコマンドパターンの使い分け基準を一度言語化する。 状態サイズ・操作の可逆性コスト・実装工数のどれを優先するかを決めておくと、次にUndoが必要になった時に即決できる。

  6. スキーマの「加算的後方互換」が通用する限界を見極めておく。 フィールドの意味変更や削除が必要になった時点で加算方式は破綻するため、その時のための簡易マイグレーション戦略を今のうちに一行メモしておく。
